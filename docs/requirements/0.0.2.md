# 0.0.2 요구사항

상태: 충족 · 날짜: 2026-10-23

0.0.1 과 반대 방향으로 쓴다. 0.0.1 은 구현된 것을 요구사항으로 정의했고, 이 문서는
**구현보다 먼저** 무엇이 되어야 하는가를 정한다. 설계는 [0004](../design/0004-스냅샷-비교.md) 에 있다.

[0.0.1 의 요구사항](0.0.1.md) R1~R14 는 그대로 유지한다. 여기에는 **더하거나 바꾸는 것만** 적는다.
강제 수단의 뜻도 0.0.1 과 같다.

열린 질문 다섯은 닫혔다 (§5). 설계는 0004 가 받아 썼고, 그대로 구현했다.

## 1. 범위

### 1.1 하는 것

**스냅샷 간 비교.** 객체 저장소에 쌓인 두 스냅샷 사이에서 어떤 문서·노드·블록이 바뀌었는지를
주소로 말한다. 0.0.1 이 비목표로 미뤘고 (0.0.1 §1.2), 0002 §10 과 0003 §8 이 남은 일로 적었다.

내용 주소 저장소가 이 기능을 싸게 만든다. 주소가 같은 하위 트리는 한 글자도 다르지 않으므로
열어 보지 않고 건너뛸 수 있고, 비교 비용이 문서 수가 아니라 **바뀐 곳**에 비례한다.

### 1.2 하지 않는 것 (비목표)

0.0.1 §1.2 의 비목표는 `diff` 를 빼고 그대로 이어진다. 더하는 것:

| 비목표 | 근거 |
| --- | --- |
| 작업 트리와 Git 커밋의 비교 | 이력의 원본은 Git 이다 (0003 §2.2). 그쪽은 `git diff` 가 한다 |
| 두 저장소 사이의 비교 | 저장소를 주고받지 않는다 (0002 §7) |
| 팩파일·델타 체인 | 0002 §7 의 조건 셋이 아직 하나도 서지 않았다. 이 저장소의 객체는 62 개다 |
| 저장소에 아직 쌓이지 않은 작업 트리와의 비교 | §5 Q5 — 먼저 `store` 를 돌린다. R15.9 를 지킨다 |
| 파일 시스템 감시로 파일마다 남는 `stat` 없애기 | §5 Q3 — 0.0.1 에서 미룬 최적화를 다시 미룬다 |
| 문서 디렉터리를 두 번 읽는 것 (`existsSync` 뒤 `readdir`) 줄이기 | §5 Q3 — 같다 |

## 2. 스냅샷 비교 (R15)

| ID | 요구사항 | 강제 |
| --- | --- | --- |
| R15.1 | `dockit diff <앞> <뒤>` 는 두 스냅샷을 비교한다. `<뒤>` 를 생략하면 HEAD 다 | 테스트 |
| R15.2 | 스냅샷 주소는 `cat` 처럼 앞부분만 줘도 된다. 여럿과 겹치면 실패한다 | 테스트 |
| R15.3 | 변경마다 0.0.1 의 주소 문법(`문서#조각`)으로 위치를 말한다 | 테스트 |
| R15.4 | 변경의 종류는 생김 · 사라짐 · 바뀜 · 옮김 넷이다 | 타입 |
| R15.5 | 바뀜은 무엇이 바뀌었는지를 가른다 — 본문(blob) · 보조데이터(항목 메타) · 제목 · 타입(문서) | 테스트 |
| R15.6 | **주소가 같은 하위 tree 는 열지 않는다.** 읽는 객체 수가 바뀐 곳에 비례한다 | 테스트 |
| R15.7 | 이름 없는 블록 하나를 끼우거나 빼도, 그 뒤 블록들이 모두 바뀜으로 나오지 않는다 | 테스트 |
| R15.8 | 위치만 바뀐 것은 변경이 아니다 — 줄 번호, 파일 경로, 한 파일과 노드 디렉터리 사이의 형태 전환 | 테스트 |
| R15.9 | 비교는 저장소만 읽는다. 작업 트리와 규약을 읽지 않고, 아무것도 쓰지 않는다 | 테스트 |
| R15.10 | 가리킨 스냅샷이 저장소에 없으면 실패한다. 이력이 잘려 있으면(끊긴 부모, R11.10) 거둔 이력일 수 있다고 덧붙인다 | 테스트 |
| R15.11 | `--json` 은 같은 결과를 낸다. 실패는 R13.3 처럼 `{ error }` 다 | 테스트 |
| R15.12 | 옮김은 **같은 부모 안에서** 자리만 바뀐 블록·섹션이다. 부모가 바뀌면 사라짐과 생김이다 | 테스트 |
| R15.13 | 기본 출력은 주소와 종류뿐이다. `--patch` 를 주면 본문이 바뀐 블록에 줄 단위 차이를 붙인다 | 테스트 |
| R15.14 | 종료 코드는 기본 0 이다. `--exit-code` 를 주면 차이가 있을 때 1 이다. 실패는 늘 2 다 | 테스트 |

R15.6 이 이 기능의 존재 이유다. 문서 1000 개 중 하나를 고쳤다면 뿌리에서 그 문서까지의 tree
몇 개와 바뀐 노드만 읽어야 한다. 테스트는 저장소가 읽은 객체 수를 센다.

R15.7 은 R9.4 에서 나온다. tree 항목은 순서를 지키고 블록에는 이름이 없으므로, 자리끼리
맞추면 블록 하나를 끼운 것이 그 뒤 전부의 변경으로 보인다. 안정 식별자가 있는 블록은 그것으로,
없는 블록은 내용 주소로 먼저 짝을 짓고 남은 것만 비교한다.

R15.12 는 그 짝짓기에서 거저 나온다. 짝이 지어졌는데 자리가 다르면 옮김이다. 순서가 뜻을 갖는
도구라서 (R9.4) "순서만 바꿨다" 는 사실 자체가 정보다. 부모를 넘나드는 짝은 찾지 않는다 —
찾으려면 두 스냅샷의 블록 전부를 모아야 해서 R15.6 이 무너진다.

R15.13 은 R8.1 과 같은 발상이다. 읽는 쪽의 토큰을 아끼고, 내용이 필요하면 한 번 더 묻게 한다.

R15.8 은 R9.6 에서 거저 얻는다. 위치는 주소에 들어가지 않으므로 같은 내용이면 같은 tree 다.
`split` 한 문서는 비교 결과가 비어야 한다.

### 2.1 R15.10 과 보존 정책

`head` 정책에서 거두기를 돌리면 HEAD 하나만 남는다 (R11.6). 그 프로젝트에서 `diff` 는
다음 거두기 전까지 쌓인 스냅샷 사이에서만 쓸 수 있다. 이 기능은 사실상 `all` 프로젝트의 것이다
(0003 §8). 실패 메시지가 이 사정을 알려야 한다 — "없는 주소" 와 "거둔 이력" 은 사용자가 할 일이 다르다.

다만 둘을 확실히 가를 수는 없다. 거둔 이력은 기록하지 않으므로 (0003 §2.2) 지워진 주소를 알 길이
없다. 아는 것은 HEAD 에서 거슬러 오르다 끊긴 부모를 만났다는 사실뿐이고, 그때만 "거둔 이력일 수
있다" 고 말한다. 이력이 끊기지 않았다면 그냥 없는 주소다.

## 4. 인수 조건

0.0.1 §16 의 넷이 그대로 통과하고, 더해서:

- R15 의 테스트가 모두 통과한다
- `rules/` 에서 문서 하나를 고치고 `store` → `diff` 를 돌리면 그 노드만 나온다
- `rules/` 의 문서 하나를 `split` 하고 `store` → `diff` 를 돌리면 결과가 비어 있다

```bash
npm run typecheck   # 타입 (src + test)
npm test            # 261 개
npm run build       # 산출물
npm run check       # 자기 자신을 자기 자신으로 검사 — 진단 없음
```

## 5. 정한 것

초안의 열린 질문 다섯과 그 답이다. 고르지 않은 쪽도 남겨, 왜 이렇게 됐는지 다시 따질 때 쓴다.

| | 질문 | 정한 것 | 고르지 않은 것 | 까닭 |
| --- | --- | --- | --- | --- |
| Q1 | 본문이 바뀐 블록의 글자 단위 차이 | `--patch` 일 때만 (R15.13) | 주소만 · 늘 붙이기 | 기본은 짧게, 필요하면 한 번 더 묻는다 (R8.1) |
| Q2 | 차이가 있을 때 종료 코드 | `--exit-code` 일 때만 1 (R15.14) | 늘 0 | `git diff` 와 같다. CI 에서 "바뀐 것 없음" 을 확인할 길이 남는다 |
| Q3 | 0.0.1 에서 미룬 최적화 | 다시 미룬다 (§1.2) | 둘 다 · 두 번 읽기만 | 측정한 병목이 없다 — 파일 2000 개에서 캐시가 다 맞는 인덱싱이 약 80ms. 0.0.2 는 비교 하나에 모은다 |
| Q4 | 순서만 바뀐 블록·섹션 | 옮김 (R15.4 · R15.12) | 사라짐 + 생김 | 짝짓기(R15.7)에서 거저 나오고, 순서가 뜻을 갖는다 (R9.4) |
| Q5 | 쌓이지 않은 작업 트리와 HEAD 의 비교 | 하지 않는다 (§1.2) | 쓰지 않는 인덱싱을 돌려 비교 | 비교는 저장소만 읽는다 (R15.9). 먼저 `store` 를 돌리면 된다 |
