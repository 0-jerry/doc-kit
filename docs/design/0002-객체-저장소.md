# 객체 저장소 — 내용 주소 인덱싱

상태: 구현 완료 · 날짜: 2026-10-15

> 0001 이 "도구가 도메인을 모르게" 만들었다. 이 문서는 그 결론을 한 걸음 더 밀어
> **도구가 판단기준도 모르게** 하고, 인덱싱 비용을 내용 주소화로 떨어뜨린다.

## 1. 배경과 문제

### 1.1 이름이 실제보다 좁았다

0001 은 목표를 "도구가 도메인을 모르게 하는 것"으로 적고 그대로 구현했다. 문서 타입·섹션
문법·역할·어휘가 전부 선언으로 빠졌고, 내장 프리셋조차 사용자 선언과 같은 로더를 탄다.
그런데 README 는 여전히 "판단기준을 다루는 도구"로 자기를 소개했다.

실제 엔진이 아는 것은 셋뿐이다.

| 아는 것 | 어디에 |
| --- | --- |
| 블록 단위 트리와 보조데이터 상속 | `model/` |
| 노드가 책임을 넘지 못하게 하는 제약 | `validate/` |
| 조각을 질의하고 조작하는 프로토콜 | `query/` `api/` |

"판단기준"은 `preset/principle` 이라는 **프리셋 이름에만** 남아 있다. 그러니 이 라이브러리는
**문서 구조화 도구**이고, 판단기준은 그 도구로 할 수 있는 한 가지다. 문서를 그렇게 고친다.

### 1.2 인덱싱에 지속성이 없었다

`loadWorkspace` 는 매 실행마다 전부 다시 한다.

```
collectSources  → 전체 파일 읽기
parseDocument   → 전체 파싱
validateDocument→ 전체 검증
recordsOf       → 전체 납작하게 펴기
buildGraph      → 역인덱스와 관계 그래프
```

문서 하나를 고쳐도 전체 비용을 다시 낸다. `dockit index --out` 은 그 결과를 JSON 으로 쏟는
것뿐이고, 다음 실행은 그 JSON 을 쳐다보지 않는다. 에이전트가 문서를 고치며 되묻는 쓰임에서는
이 비용이 매번 걸린다.

## 2. 결정

| 항목 | 결정 | 왜 |
| --- | --- | --- |
| 저장소의 위치 | **파생물**. 마크다운이 원본 | 0001 의 "원문을 지킨다" 와 충돌하지 않는다 |
| 이력 | 스냅샷 체인을 남긴다 | 수명주기 필드가 이미 있으니, 언제 바뀌었는지도 데이터여야 한다 |
| 해시 입도 | 블록이 blob, 노드가 tree | 모델이 이미 그 모양이다 (§3) |
| 해시 | SHA-256 | Git 의 SHA-1 충돌 내력을 물려받을 이유가 없다 |
| 압축 | 객체마다 zlib deflate | Git 의 느슨한 객체와 같다 |
| 팩파일·델타 | **하지 않는다** | §7 |

## 3. 왜 Git 구조가 맞아떨어지는가

이식이 아니다. 0001 이 이미 내용 주소 구조를 만들어 놓았고, 주소만 부여하지 않았다.

0001 §4.1 은 이렇게 적었다.

> 노드는 **자기가 정의한 내용**과 **하위 노드 인덱스**만 소유한다. 부모가 자식을
> 소유하지 않으므로 노드 하나를 읽는 데 다른 노드가 필요 없고, 합치는 일은
> 인덱스를 따라 끼워 넣는 것뿐이다.

이것이 Git tree 의 정의다. 그리고 `children: [norm, rationale, example]` 는 문자 그대로
tree entry 목록이다.

| Git | doc-kit |
| --- | --- |
| blob — 이름 없는 내용 | 블록 (문단·목록·코드·표·인용) |
| tree — 이름과 해시의 목록 | 노드 (문서·섹션) |
| commit — 뿌리 tree + 부모 | 스냅샷 |
| index 의 stat 캐시 | `StatCache` (없었다) |

### 3.1 다른 점 — 항목을 정렬하지 않는다

Git 은 tree 항목을 이름으로 정렬한다. 파일시스템 순서에 뜻이 없기 때문이다.
여기서는 **순서가 곧 문서 순서**라서 정렬하면 뜻이 바뀐다. 그래서 노드 tree 는
주어진 순서를 지키고, 순서가 다르면 다른 주소가 된다.

고유한 순서가 없는 자리 — 컬렉션과 문서 — 에서는 이름으로 정렬한다. 결정적이기만 하면 되고,
정렬이 그 자리에서는 가장 단순한 결정적 순서다.

### 3.2 무엇을 해싱하고 무엇을 빼는가

```
담는다 — 본문 · 형태 · 보조데이터 · 순서 · 제목 · 안정 식별자
뺀다   — 줄 번호 · 파일 경로 · 원문 조각
```

뺀 것들은 **내용이 아니라 위치**다. 파일을 옮기거나 위쪽에 줄 하나를 넣어도 주소가 그대로여야
캐시가 살아남는다. 보조데이터는 정규 JSON(키 재귀 정렬)으로 적어, 선언 순서가 달라도 같은 뜻이면
같은 바이트가 된다.

## 4. 층

```
  store/                 바이트만 안다. 프로젝트의 어떤 층도 import 하지 않는다
    hash.ts              테두리와 SHA-256
    wire.ts              blob · tree · snapshot 의 바이너리 표현, LEB128, 정규 JSON
    objects.ts           느슨한 객체 저장소, HEAD, 이력
    stat-cache.ts        경로 → (수정시각, 크기, 내용해시)
    derived.ts           파생 데이터 캐시
                   ▲
                   │ 이 경계를 넘는 파일은 둘뿐이다
                   │
  workspace/encode.ts      문서 → 객체
  workspace/incremental.ts 증분 인덱싱
```

`model` 이 아무것도 import 하지 않고(P0) `store` 도 아무것도 import 하지 않으므로(P0'),
문서와 바이트를 잇는 일이 한곳으로 모인다. 층 테스트가 이것을 고정한다 —
`store/` 를 import 하는 파일이 둘보다 늘어나면 실패한다.

## 5. 비용이 떨어지는 자리

단축 경로는 두 단계이고, 아끼는 것이 서로 다르다.

```
1. stat 캐시   수정시각·크기가 그대로 → 파일을 읽지 않는다        (I/O)
2. 원본 해시   문서를 이루는 파일들의 내용 해시가 그대로
               → 파싱·검증을 건너뛰고 지난 기록·진단을 그대로 쓴다  (CPU)
```

1 이 없으면 2 를 판정하려고 전부 읽어야 한다. 2 가 없으면 읽기만 아끼고 실제 비용인 파싱과
검증은 그대로 낸다. **둘이 같이 있어야 이득이 난다.**

열쇠에는 규약 해시를 접어 넣는다. 규약이 바뀌면 해석 결과가 전부 달라지므로 캐시가
통째로 무효가 되어야 한다.

### 5.1 문서 트리는 지연 파싱한다

캐시가 맞으면 파싱하지 않으므로 `Document` 객체가 없다. 그런데 `query` `context` `check`
`index` 는 납작한 기록만으로 끝난다 — 트리가 필요한 것은 `assemble` `render` `apply` 뿐이다.

그래서 `WorkspaceEntry.document` 를 **읽을 때 파싱**하게 두었다. 질의 경로는 한 번도
파싱하지 않고, 트리가 필요한 쪽만 값을 치른다.

### 5.2 블록 단위 blob 이 사는 자리

블록을 blob 으로 끊으면 셋째 이득이 생긴다. 같은 진술이 여러 문서에 있으면 저장소에 한 번만
담긴다 — `write` 가 이미 있는 주소에 다시 쓰지 않기 때문이다. 이것은 증분 인덱싱과 무관한,
저장 공간과 중복 탐지 쪽의 이득이다.

### 5.3 되돌리면 되돌아온다

내용 주소화의 성질이라 따로 구현하지 않아도 따라온다. 문서를 고쳤다가 되돌리면 뿌리 tree 주소가
원래 값으로 **정확히** 돌아오고, 스냅샷은 새로 쌓이지 않는다. 자기 자신의 `rules/` 에서 측정한 값:

```
처음        문서 4 — 캐시 0 · 파싱 4 | 파일 읽음 21 | 객체 새로 43
다시        문서 4 — 캐시 4 · 파싱 0 | 파일 읽음  0 | 객체 새로  0   스냅샷 그대로
한 줄 고침  문서 4 — 캐시 3 · 파싱 1 | 파일 읽음  1 | 객체 새로  6
되돌림      문서 4 — 캐시 4 · 파싱 0 | 파일 읽음  1 | 뿌리 주소 원래대로
```

되돌린 뒤 파일을 하나 읽은 것은 수정시각이 바뀌어서다 — 읽어 해싱해 보고 내용이 같음을
확인한 뒤 파싱을 건너뛴다. 두 단계가 각각 제 일을 한 모습이다.

## 6. 파일 배치

```
.dockit/store/
  objects/ab/cdef…        zlib(`<타입> <길이>\0<내용>`)
  derived/ab/cdef….z      zlib(JSON) — 기록과 진단. 지워도 느려질 뿐 틀리지 않는다
  index                   stat 캐시. "DKIX" + 버전 + 개수 + 항목
  HEAD                    마지막 스냅샷 주소
```

전부 `.gitignore` 대상이다. 원본은 마크다운이고 이쪽은 재생성할 수 있다 — 층 테스트가 아니라
`저장소를 지워도 결과는 같다` 테스트가 이것을 지킨다.

## 7. 하지 않은 것 — 팩파일과 델타 체인

Git 의 packfile·`.idx`·OFS/REF 델타는 **수백만 객체와 네트워크 전송**에 대한 답이다. 규칙집은
문서 수백 개 규모이고, 객체는 블록 하나만큼 작고, 네트워크로 보내지 않는다. 느슨한 객체 하나가
파일 하나인 지금 구조에서 조회는 `stat` 한 번이고, 그보다 빠를 이유가 없다.

지금 구현하면 코드량이 수 배가 되면서 **측정 가능한 이득은 없다.** 필요해질 조건을 적어 둔다.

- 객체가 10만 개를 넘어 디렉터리 항목 수가 문제가 될 때
- 저장소를 원격으로 주고받게 될 때
- 같은 문서의 긴 판본이 쌓여 델타가 실제로 짧아질 때

그때 `objects/` 를 읽어 `pack/` 을 만드는 `gc` 를 더하면 된다. 테두리와 주소 규약은 그대로
쓸 수 있도록 지금 형식을 정해 두었다.

## 8. CLI

```bash
dockit store [루트]     저장소를 갱신하고 통계를 낸다
dockit log   [루트]     스냅샷 이력
dockit cat   <주소>     객체 하나를 들여다본다
```

`index` 도 같은 증분 경로를 탄다. `--store <경로>` 로 저장소를 옮길 수 있고, 기본은
루트가 속한 프로젝트의 `.dockit/store` 다 — 보존 정책을 찾는 바로 그 바탕(`projectBase`)이다.

## 9. 트레이드오프

| 얻은 것 | 낸 값 |
| --- | --- |
| 바뀌지 않은 문서의 파싱·검증을 건너뛴다 | `stat` 은 여전히 전체 파일에 돈다 |
| 같은 내용 블록이 한 번만 저장된다 | 객체 수가 블록 수만큼 많아진다 |
| 규칙집의 변경 이력을 데이터로 본다 | 스냅샷이 쌓인다 ([0003](0003-거두기.md) 이 거두기로 메운다) |
| 저장소를 지워도 안전하다 | 지운 다음 한 번은 전체 비용을 낸다 |

`stat` 을 전체 파일에 도는 것은 Git 도 같다. 처음에는 디렉터리 수정시각으로 줄일 수 있다고
적었으나, 재 보고 접었다.

- 디렉터리 수정시각은 항목이 생기거나 사라질 때만 바뀐다. **파일 내용이 바뀐 것은 그 파일의
  수정시각에만 나타나므로**, 파일마다 `stat` 한 번은 줄일 수 없다. 없애려면 파일 시스템 감시가 있어야 한다
- 디렉터리 수정시각을 확인하는 것도 디렉터리마다 `stat` 한 번이라, 아끼는 것은 `readdir` 을
  `stat` 으로 바꾸는 것뿐이다. 그 대가로 결과가 파일 시스템의 수정시각 정확성에 기대게 된다

실제로 줄일 것은 구조를 알아내는 데 쓰던 호출이었다. 항목마다 디렉터리인지 `stat` 으로 묻고
`node.md` 가 있는지 따로 물었는데, `readdir` 이 항목의 종류를 함께 돌려주므로 둘 다 필요 없다.
파일 2000 개 · 디렉터리 1602 개에서 캐시가 다 맞는 인덱싱의 파일 시스템 호출이
10807 → 5606 으로 줄었다. 로컬 SSD 에서 걸린 시간은 그대로(약 80ms)였다 — `stat` 이 싼 곳에서는
병목이 아니고, 네트워크 파일 시스템처럼 `stat` 이 비싼 곳에서 차이가 난다.
