# 거두기 — 보존 정책과 미참조 객체

상태: 구현 완료 · 날짜: 2026-10-15

> 0002 가 저장소를 만들면서 거두기를 §10 으로 미뤘다. 그 미룸이 실제로 얼마나 새는지
> 재 보니 미룰 수준이 아니었다. 이 문서는 그 구멍과, 메우면서 함께 바로잡은 것을 적는다.

## 1. 실측된 누수

문서 10 개를 두고 **그중 하나만** 50 번 고치며 쟀다.

| 고침 | objects | derived | 바이트 |
| --- | --- | --- | --- |
| 1 | 37 | 10 | 9,422 |
| 10 | 109 | 19 | 24,971 |
| 25 | 229 | 34 | 50,931 |
| 50 | **429** | **59** | **94,199** |
| *같은 트리를 빈 저장소에 담으면* | *37* | *10* | *9,427* |

고침 하나마다 객체 8 개와 파생 항목 1 개가 쌓이고 **상한이 없다**. 50 번 뒤 저장소의 92% 가
작업 트리와 무관하다. 성질이 다른 두 누수다.

- **`derived/`** — 순수 쓰레기다. 열쇠가 내용 지문이라 다시 맞을 일이 없는데 축출 수단이
  아예 없었다. 변호할 여지가 없는 빠뜨림이다.
- **`objects/`** — 스냅샷 체인에서 닿으므로 명목상 이력이다. 다만 거두기도 깊이 제한도 없었으니
  **무한 이력을 고른 것이 아니라 고르지 않은 것**이다. 0002 §9 에 "스냅샷이 쌓인다" 한 줄로
  적고 넘어간 것이 문제였다.

## 2. 결정

| 항목 | 결정 |
| --- | --- |
| 정책을 누가 정하는가 | **프로젝트가 초기화할 때** 정하고 그 뒤로 바꾸지 않는다 |
| 정책 | `head` (기본) 또는 `all`. 둘뿐이다 |
| `head` | HEAD 에서 닿는 것만 남긴다 |
| `all` | 이력을 전부 보존한다. 그 대가로 **거두기를 돌리지 않는다** |
| 지운 이력의 기록 | **남기지 않는다** |
| 설정의 위치 | `.dockit/store.yaml`. 저작 규약과 섞지 않는다 |

### 2.1 왜 둘뿐인가

`--keep n` 같은 중간값을 두지 않았다. 이력에 대한 요구는 실제로 둘로 갈린다 —
되돌아볼 생각이 있으면 전부 있어야 쓸모가 있고, 없으면 하나만 있으면 된다. 중간값은
"있는 줄 알았는데 그만큼은 없는" 상태를 만든다.

그래서 정책이 거두기의 **매개변수가 아니라 거두기의 존재 여부**다. `all` 을 고른 프로젝트에서
`gc` 는 아무것도 하지 않고 그 이유를 말한다. `--force` 로 뚫리지 않는다 — 뚫리면 설정의 뜻이 없다.

### 2.2 왜 기록을 남기지 않는가

압축 로그를 두는 안을 검토했고 접었다. 로그가 쓸모 있으려면 바뀐 노드 주소와 줄까지 담아야 하고
(메타데이터만으로는 `log` 가 지금 주는 것과 같다), 그만큼 담기 시작하면 로그가 제2의 저장소가
된다. 거두기의 뜻이 사라진다.

대신 선택을 정직하게 만들었다. `head` 를 고르는 것은 **이력을 버리기로 하는 것**이고,
`init` 이 그 자리에서 "되돌릴 수 없습니다" 라고 말한다. 이력이 필요하면 `all` 을 고른다.

### 2.3 설정이 규약과 따로 있는 이유

`schema.yaml` 은 "무엇을 쓸 수 있는가" 를 답하는 L1 저작 규약이다. 보존 정책은 저장의 문제이고
저작과 아무 관계가 없다. 한 파일에 담으면 규약을 읽는 모든 곳이 저장 정책도 알게 된다.

### 2.4 정책은 cwd 를 타고 새지 않는다

규약(`resolveSchema`)은 루트 → 루트의 부모 → cwd 순으로 찾는다. 보존 정책은 **cwd 를 보지 않는다.**

규약이 어긋나면 진단이 어긋날 뿐이지만 보존 정책은 파일을 지운다. 남의 루트를 인수로 주고
거두기를 돌릴 때 이쪽 정책이 따라가면, 그 프로젝트가 고른 `all` 을 무시하고 이력을 지운다.
테스트가 이 차이를 고정한다.

**저장소도 같은 바탕에서 찾는다.** 정책만 루트를 따르고 저장소가 cwd 를 따르면, 남의 정책이
이쪽 저장소를 거둔다. 그래서 기본 저장소는 `projectBase(root)/.dockit/store` 다.

## 3. 알고리즘

두 디렉터리의 성질이 달라 정책도 다르다.

```
objects/   도달성으로 판정한다
           뿌리(HEAD)에서 표시하고, 표시되지 않은 것을 쓸어낸다.
           내용 주소 저장소에서 도달성은 곧 필요성이다 — 닿지 않으면 되살릴 길이 없다.

derived/   도달 개념이 없다. 열쇠가 주소가 아니라 내용 지문이다.
           그래서 인덱싱을 한 번 돌려 실제로 쓰인 열쇠를 모으고 나머지를 버린다.
```

`markFrom` 은 **스냅샷의 부모를 따르지 않는다**. 얼마나 거슬러 올라갈지는 정책이고, 부르는 쪽이
뿌리 목록으로 표현한다 — `store/sweep.ts` 는 정책을 모른다. 0002 §4 의 경계를 그대로 지킨다.

### 3.1 끊긴 부모를 고쳐 쓰지 않는다

거둔 뒤 HEAD 의 `parents` 는 이미 없는 스냅샷을 가리킨다. 고쳐 쓰고 싶지만 그러면 **HEAD 자신의
주소가 바뀐다** — 내용 주소에서 부모는 내용의 일부다. 그래서 끊긴 채 둔다. `history()` 가
`snapshot()` 이 null 이면 멈추므로 `log` 는 그대로 동작하고, 끊긴 링크는 "여기서 이력이 잘렸다" 는
사실을 남긴다.

## 4. 거두기를 안전하게 만드는 불변식

> 진단은 문서와 규약만의 함수다. 저장소에 무엇이 담겨 있는지가 결과를 바꾸어서는 안 된다.

이 불변식이 서면 거두기가 **구조적으로** 안전하다. 지우는 일이 진단을 바꿀 수 없으므로 최악이
다음 실행 한 번 느려지는 것뿐이고, 무엇을 언제 지워도 되는지 따로 따질 필요가 없다.

0002 에서는 이것이 규율로만 지켜졌다. 이제 셋이 고정한다.

1. `rules/principle/진단은-저장소-상태에-의존하지-않는다` — 자기 자신의 원칙으로 적었다
2. `저장소를 지워도 결과는 같다` 테스트를 **진단까지** 확장했다 (기록만 보면 새는 것을 놓친다)
3. `거두기는 진단과 기록을 바꾸지 않는다` 테스트 — 거두기 전후를 직접 비교한다

파생 캐시가 진단을 담는 것은 이 원칙을 깨지 않는다. 열쇠가 내용 지문이므로 같은 내용이면 반드시
같은 진단이고, 지우면 다시 계산할 뿐이다.

## 5. 측정값

§1 의 상황(문서 10 개, 하나를 50 번 고침)에서:

```
거두기 전   객체 429 · 파생 59 · 스냅샷 50 개
--dry-run   객체 429 → 37 (거둠 392) · 파생 59 → 10 (거둠 49) · 실제로는 그대로
거둔 뒤     객체  37 · 파생 10 · 스냅샷 1 개 (끊긴 부모에서 멈춤)

불변식      진단 같은가: true · 기록 같은가: true · 뿌리 주소 같은가: true
정책 all    건너뜀: true · 거둔 객체 0
```

남은 37 개는 같은 작업 트리를 빈 저장소에 담았을 때와 **정확히 같은 수**다. 거듭 거두어도 더
줄지 않는다.

## 6. 함께 바로잡은 것 — REF001

0002 §10 에 "REF001 을 해시 조회로 바꾸기" 를 적었다. **틀렸다.** 두 가지 이유로 철회한다.

**첫째, §4 의 불변식을 깬다.** blob 주소로 판정하면 저장소에 남은 과거 판본의 블록까지 비교
대상이 된다. 지금 어느 문서에도 없는 진술을 중복이라 말하고, 거두기를 돌리면 같은 문서에 다른
진단이 난다. 이 설계가 거두기를 못 하게 만들었을 것이다.

**둘째, 효율 전제 자체가 틀렸다.** 현재 구현은 이미 정규화한 본문을 열쇠로 `Map` 에 넣는다 —
이미 해시 그룹핑이다. 재 보니 해시를 한 겹 더 씌우는 쪽이 모든 규모에서 더 느렸다.

| 블록 수 | 현재 | 배열 재생성만 제거 | 해시 조회 |
| --- | --- | --- | --- |
| 200 | 0.249 ms | **0.160** | 0.323 |
| 5,000 | 6.34 ms | **3.33** | 5.10 |
| 50,000 | 86.0 ms | **51.2** | 64.4 |

이득은 전부 다른 데 있었다. `groups.set(key, [...(groups.get(key) ?? []), record])` 가 중복마다
배열을 다시 만들고, `normalizeText` 를 레코드당 두 번 불렀다. 그 둘만 고쳐 1.7 배가 됐다.

덧붙여 blob 주소는 **바이트 정확**이고 `normalizeText` 는 공백·대소문자를 무시한다. 바꾸면
탐지가 조용히 줄어든다 — 더 빠르지도, 더 정확하지도 않았다.

## 7. 트레이드오프

| 얻은 것 | 낸 값 |
| --- | --- |
| 저장소 크기가 작업 트리에 비례해 유계가 된다 | `head` 를 고르면 이력을 영구히 버린다 |
| 거두기가 진단을 바꿀 수 없음이 테스트로 선다 | 거두기 전에 인덱싱을 한 번 돌려야 한다 |
| 정책이 둘뿐이라 상태가 단순하다 | 중간 보존(최근 n 개)을 못 고른다 |
| 정책이 남의 루트로 새지 않는다 | 규약 찾기와 탐색 순서가 다르다 (§2.4) |
| `all` 이 이력을 온전히 지킨다 | 그 프로젝트의 저장소는 계속 자란다 |

거두기가 인덱싱을 먼저 돌리는 것은 피할 수 없다. 작업 트리의 객체가 뿌리에서 닿는 상태가
되어야 쓸어내기가 그것을 지우지 않는다.

## 8. 남은 것

- `dockit diff <주소> <주소>` — 0002 §10 에 적은 그대로 유효하다. 뿌리 tree 주소가 같은 하위
  트리를 통째로 건너뛸 수 있어 비교 비용이 바뀐 곳에 비례한다. 다만 `head` 정책에서는 거둔 뒤
  비교할 상대가 없으므로, 실질적으로 `all` 프로젝트의 기능이다
- `objects/` 가 10 만 개를 넘을 때의 팩파일. 조건은 0002 §7 에 적어 두었다
