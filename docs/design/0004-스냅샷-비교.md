# 스냅샷 비교 — `dockit diff`

상태: 구현 완료 · 날짜: 2026-10-23

> [0.0.2 요구사항](../requirements/0.0.2.md) R15 를 받아 쓴다. 요구사항이 "무엇" 을 정했고,
> 이 문서는 "어떻게" 와 "왜 그렇게" 를 적는다. 구현은 이 문서 뒤에 온다.

## 1. 출발점 — 이미 있는 것

비교에 필요한 것은 0002 가 거의 다 만들어 두었다. 새로 짓는 것은 짝짓기와 출력뿐이다.

```
스냅샷 ──root──▶ 뿌리 tree
                   ├─ 컬렉션 tree  (이름순)
                   │    └─ 문서 tree  (이름순, meta: id · type · aux)
                   │         ├─ 섹션 tree  (항목 이름 = key, meta: key · heading · depth · stableId · aux)
                   │         │    └─ …
                   │         └─ 블록 blob (항목 이름 = stableId 또는 '', 항목 meta: form · aux)
```

이 구조에서 바로 나오는 성질 넷이 설계 전체를 받친다.

1. **주소가 같으면 하위 전체가 같다.** 내용 주소이므로 tree 주소 하나가 그 아래 모든 바이트를
   대표한다. R15.6 의 근거다
2. **위치는 주소에 없다** (R9.6). 줄 번호도 파일 경로도 해싱하지 않는다. 한 파일 문서를 `split` 해도
   뿌리 주소가 그대로임을 확인했다 — R15.8 은 따로 할 일이 없다
3. **tree 항목의 자리 = 문서 모델의 자식 자리.** `encode` 가 `children` 을 그대로 항목으로 옮기므로,
   블록의 주소 걸음 `#norm/2` 의 `2` 는 항목 번호와 같고, 섹션의 `norm~2` 는 같은 이름 항목의
   순번과 같다. **파싱하지 않고 tree 만으로 0.0.1 주소를 만들 수 있다** (R15.3 · R15.9)
4. **블록 본문과 블록 보조데이터가 다른 곳에 산다.** 본문은 blob 주소, 보조데이터와 형태는 부모
   tree 의 항목 meta 다. 섹션은 제목·보조데이터가 자기 tree 의 meta 에 있다. R15.5 의 구분이 이
   경계를 그대로 따른다

## 2. 층과 파일

```
store/objects.ts      읽은 객체 수를 센다 (stats.read). 그 밖에는 바꾸지 않는다
workspace/encode.ts   tree meta 를 읽는 함수를 내보낸다 — 형식을 아는 곳은 여전히 여기 하나다
workspace/diff.ts     새 파일. 두 스냅샷을 걸어 내려가며 변경을 모은다
workspace/patch.ts    새 파일. 두 문자열의 줄 단위 차이. 저장소를 모른다
cli/main.ts           diff 명령
```

### 2.1 왜 `workspace/` 인가

비교는 항목 meta 가 무엇을 뜻하는지 — 블록인지 섹션인지, 이름이 안정 식별자인지 섹션 키인지 —
알아야 한다. `store/` 는 바이트만 알아야 하므로 (R9.7) 거기 둘 수 없다. R9.9 의 울타리가 셋에서
넷이 되고, `layering.test.ts` 의 목록에 `workspace/diff.ts` 를 적는다.

### 2.2 형식을 아는 곳은 하나로 둔다

`encode.ts` 는 "문서 → 객체 변환을 아는 유일한 곳" 이다 (`layering.test.ts`). `diff.ts` 가 meta 의
키 이름(`heading`, `form`, `aux`)을 직접 읽기 시작하면 형식을 아는 곳이 둘이 된다. 그래서 encode 가
읽기 쪽도 내보낸다.

```ts
// workspace/encode.ts
export function sectionMetaOf(tree: Tree): SectionMeta | null    // key · heading · stableId · aux
export function blockMetaOf(entry: TreeEntry): BlockMeta | null  // form · stableId(항목 이름) · aux
export function documentMetaOf(tree: Tree): DocumentMeta | null  // id · type · aux
```

쓰는 함수 옆에 읽는 함수가 있으므로, 형식을 바꾸면 한 파일 안에서 두 쪽이 함께 바뀐다.

## 3. 알고리즘

### 3.1 위에서 아래로, 같으면 멈춘다

```
diff(앞, 뒤):
  뿌리 주소가 같다 → 끝 (객체 2 개 읽음: 스냅샷 둘)
  컬렉션을 이름으로 맞춘다     — 한쪽에만 있으면 그 아래 문서 전부가 생김/사라짐
    주소가 같다 → 건너뜀
    문서를 이름으로 맞춘다       — 한쪽에만 있으면 생김/사라짐 (문서 하나로 낸다)
      주소가 같다 → 건너뜀
      문서 meta 비교 → 바뀜(보조데이터 · 타입)
      항목 목록 비교 (§3.2)
```

컬렉션과 문서는 이름순으로 정렬되어 있으므로 (0002 §3.1) 두 목록을 병합하듯 한 번에 맞춘다.
이름이 곧 정체이므로 짝짓기가 따로 필요 없다.

한쪽에만 있는 문서는 문서 하나의 생김/사라짐으로 내고 **그 안을 열지 않는다.** 새 문서의 블록
수십 개를 하나하나 "생김" 으로 늘어놓는 것은 정보가 아니라 소음이다. `--patch` 일 때도 같다 —
문서 전체 내용은 `assemble` 이나 `cat` 의 일이다.

### 3.2 항목 목록의 짝짓기

문서와 섹션 안에서는 이름이 정체가 아니다. 블록은 대부분 이름이 없고, 섹션은 `repeatable` 이면
같은 키가 여럿일 수 있다. 그래서 세 단계로 짝을 짓는다.

```
앞 항목 A[0..m), 뒤 항목 B[0..n)

1. 이름으로   — 블록: 안정 식별자가 같으면 짝
                섹션: 키가 양쪽에서 하나씩만 있으면 짝
2. 내용으로   — 1 에서 남은 것 중 (종류 · 이름 · meta · 주소) 가 모두 같으면 짝.
                같은 것이 여럿이면 앞에서부터 순서대로
3. 자리로     — 1·2 의 짝을 닻으로 삼아 목록을 틈으로 나눈다.
                같은 틈 안에서 남은 블록끼리, 남은 같은 키 섹션끼리 앞에서부터 짝
                → 바뀜
남은 것       — 앞에만: 사라짐 · 뒤에만: 생김
```

단계 2 가 R15.7 을 지킨다. 블록 하나를 끼우면 그 뒤 블록들은 자리만 밀렸을 뿐 내용 주소가 같으므로
단계 2 에서 짝이 지어지고, 끼운 블록 하나만 남아 생김이 된다.

단계 3 이 "고친 블록" 을 "사라짐 + 생김" 이 아니라 바뀜으로 만든다. 같은 틈 — 변하지 않은 두 블록
사이 — 에 앞에서 하나 빠지고 뒤에서 하나 생겼다면 그것은 고친 것이다. 틈 밖으로는 짝을 찾지
않는다. 틈을 넘는 짝은 추측이다.

### 3.3 옮김

짝이 정해지면, 짝들을 앞 목록 순서로 늘어놓고 뒤 목록에서의 자리를 읽는다. 그 수열의
**가장 긴 증가 부분수열** 에 든 짝은 제자리이고, 들지 못한 짝은 옮김이다 (R15.12).

```
앞:  a b c d        뒤:  a c d b
짝의 뒤 자리:  a→0  b→3  c→1  d→2
수열 0 3 1 2 의 최장 증가 부분수열 = 0 1 2 (a c d)  →  b 가 옮김
```

최장 증가 부분수열을 고르는 것은 "가장 적게 옮겼다고 보는" 해석을 고르는 것이다. `a c d` 셋이
그대로이고 `b` 하나가 뒤로 갔다고 읽는다 — `b` 를 빼고 셋을 앞으로 당겼다고 읽지 않는다.
`O(k log k)` 이고, k 는 짝의 수다.

옮김은 같은 부모 안에서만 본다 (R15.12). 다른 섹션으로 간 블록은 앞 부모에서 사라짐, 뒤 부모에서
생김이다. 부모를 넘는 짝을 찾으려면 두 스냅샷의 블록을 모두 모아야 하고, 그러면 같은 tree 를
건너뛰는 일(R15.6)이 무너진다.

옮긴 짝의 내용이 함께 바뀌었을 수 있다 (안정 식별자로 짝을 지은 경우). 그때는 종류를 옮김으로
두고 무엇이 바뀌었는지(§3.4)를 덧붙인다. 종류는 하나이고, 바뀐 것은 속성이다.

### 3.4 바뀜의 내용

짝이 지어진 두 항목의 주소가 다를 때만 연다.

| 짝 | 비교 | 결과 |
| --- | --- | --- |
| 블록 | blob 주소 | 다르면 `본문` |
| 블록 | 항목 meta 의 `form` | 다르면 `본문` — 문단이 목록이 된 것은 본문이 바뀐 것이다 |
| 블록 | 항목 meta 의 `aux` | 다르면 `보조데이터` |
| 블록 | 항목 이름 (안정 식별자) | 다르면 `보조데이터` — `dk:` 디렉티브로 보조데이터와 함께 적는 값이다 |
| 섹션 | tree meta 의 `heading` | 다르면 `제목` |
| 섹션 | tree meta 의 `aux` · `stableId` | 다르면 `보조데이터` |
| 섹션 | 항목 목록 | 다르면 **그 섹션을 바뀜으로 내지 않고 안으로 내려간다** |
| 문서 | tree meta 의 `type` · `aux` | 다르면 `타입` · `보조데이터` |

섹션의 항목이 바뀐 것은 섹션의 변경이 아니라 그 안 노드의 변경이다. 섹션은 자기 제목이나
보조데이터가 바뀌었을 때만 바뀜으로 나온다. 그래야 블록 하나를 고쳤을 때 결과가 한 줄이다.

### 3.5 주소

변경마다 0.0.1 주소를 단다. 기록(`NodeRecord.address`)과 같은 걸음 형식을 쓴다 — 블록은 형제
번호, 섹션은 `키` 또는 `키~순번` (§1 의 성질 3). 질의 결과의 주소를 그대로 들고 와서 비교 결과와
맞춰 볼 수 있어야 하기 때문이다.

| 종류 | 낸 주소 |
| --- | --- |
| 생김 | 뒤의 주소 |
| 사라짐 | 앞의 주소 |
| 바뀜 | 뒤의 주소. 앞과 다르면 앞의 주소도 |
| 옮김 | 앞의 주소와 뒤의 주소 |

안정 식별자가 있으면 따로 싣는다. 위치 주소는 스냅샷마다 다를 수 있지만 안정 식별자는 그렇지 않다.

## 4. 출력

### 4.1 사람이 읽는 것

```
$ dockit diff 3f2a9c1e04b7
3f2a9c1e04b7 → be4eea285508 (HEAD)

바뀜    principle/불변식#norm/0  본문
옮김    principle/불변식#rationale/2  ← #rationale/0
생김    principle/불변식#example/1
사라짐  convention/옛-규약

4 개
```

`--patch` 면 본문이 바뀐 블록 밑에 줄 단위 차이를 붙인다.

```
바뀜    principle/불변식#norm/0  본문
        - 객체의 불변식은 생성자에서 검증한다.
        + 객체의 불변식은 생성자에서 검증하고, 실패하면 만들지 않는다.
```

### 4.2 `--json`

```json
{
  "from": "3f2a9c1e04b7…",
  "to": "be4eea285508…",
  "changes": [
    { "kind": "modified", "address": "principle/불변식#norm/0", "changed": ["body"],
      "stableId": "core", "patch": "…" },
    { "kind": "moved", "address": "principle/불변식#rationale/2",
      "before": "principle/불변식#rationale/0" },
    { "kind": "added", "address": "principle/불변식#example/1" },
    { "kind": "removed", "address": "convention/옛-규약" }
  ]
}
```

종류의 기계 이름은 `added` `removed` `modified` `moved` 다. `changed` 의 값은 `body` `aux`
`heading` `type` 이다. `patch` 는 `--patch` 일 때만 있다.

### 4.3 순서

결과는 뒤 스냅샷의 문서 순서를 따른다 — 컬렉션 이름순, 문서 이름순, 그 안은 항목 순서. 사라진
항목은 앞에서 바로 앞에 있던 항목의 짝 뒤에 끼운다. 같은 입력이면 늘 같은 순서다.

### 4.4 종료 코드 (R15.14)

| 상황 | 코드 |
| --- | --- |
| 비교함 | 0 |
| 비교함, `--exit-code`, 차이 있음 | 1 |
| 스냅샷을 찾지 못함, 인수 오류 | 2 |

## 5. 스냅샷 찾기와 실패

```
dockit diff <앞> [<뒤>]
```

| 상황 | 동작 |
| --- | --- |
| `<뒤>` 생략 | HEAD. HEAD 가 없으면 실패 — "이력이 없습니다. `dockit store` 를 먼저 돌리세요" |
| 앞부분이 여럿과 겹침 | 실패. 겹치는 주소를 늘어놓는다 (`cat` 과 같다) |
| 주소가 스냅샷이 아닌 객체 | 실패. "스냅샷이 아닙니다: tree" |
| 주소가 없음 | 실패. 이력이 잘려 있으면 "거둔 이력일 수 있습니다" 를 덧붙인다 |

마지막 줄이 R15.10 이다. 이력이 잘렸는지는 HEAD 에서 `history()` 를 끝까지 걸어, 마지막 스냅샷에
부모가 적혀 있는데 그 부모를 읽을 수 없는지로 안다 (R11.10 의 끊긴 부모). 거둔 주소 자체는 기록이
없으므로 (0003 §2.2) 알 수 없다 — 그래서 "일 수 있습니다" 다.

`store.matching` 은 객체 종류를 가리지 않으므로, 앞부분 찾기는 겹친 것 중 스냅샷만 남긴다.
스냅샷 하나와 tree 하나가 같은 앞부분을 가졌다면 스냅샷을 고른다 — 사용자는 `log` 에서 본 앞부분을
줬을 것이다.

## 6. 저장소만 읽는다 (R15.9)

`diffSnapshots(store, 앞, 뒤)` 는 `ObjectStore` 하나만 받는다. 규약도 루트도 받지 않는다.

CLI 는 저장소를 찾기 위해서만 루트를 쓴다 — `openStore(--store, 루트)` 가 `projectBase` 로 `.dockit`
의 자리를 찾는다. 작업 트리의 문서는 열지 않는다. 테스트는 루트에 문서를 하나도 두지 않은 채
저장소만으로 비교가 되는지 본다.

읽기만 하므로 `dryRun` 저장소가 필요 없다. 아무것도 쓰지 않는다는 것은 비교 전후 저장소 디렉터리의
파일 목록과 수정시각이 같은지로 확인한다.

## 7. 비용 (R15.6)

`ObjectStore.stats` 에 `read` 를 더해 `read()` 가 디스크에서 객체를 연 횟수를 센다. 테스트가 이것으로
R15.6 을 고정한다.

문서 N 개 중 하나의 블록 하나를 고쳤을 때 읽는 객체:

```
스냅샷 2 + 뿌리 tree 2 + 컬렉션 tree 2 + 문서 tree 2 + (바뀐 섹션까지의 tree 2 × 깊이)
```

N 에 기대지 않는다. 블록 blob 은 `--patch` 일 때만 읽는다 — 바뀜을 판정하는 데는 주소 비교로 충분하다.

깊이 제한이 3 이므로 (R6.4) 블록 하나를 고친 비교는 객체 열 개 남짓을 읽는다. 테스트는 문서 수를
1 과 50 으로 바꿔 읽은 수가 같은지 본다.

## 8. 줄 단위 차이 (`patch.ts`)

블록 하나는 짧다 — 문서 전체 블록 상한이 60 이고 (R6.6) 블록은 문단 하나다. 그래서 줄 단위
최장 공통 부분수열을 `O(nm)` 표로 구한다. Myers 알고리즘은 쓰지 않는다. 블록 크기에서 차이가
없고, 코드가 세 배가 된다.

외부 의존성을 들이지 않는다. 저장소와 같은 규율은 아니지만(R9.8 은 `store/` 의 것이다) 수십 줄짜리
함수 하나를 위해 의존성을 늘릴 까닭이 없다.

## 10. 트레이드오프

| 얻은 것 | 낸 값 |
| --- | --- |
| 비교 비용이 바뀐 곳에 비례한다 | 부모를 넘는 옮김을 알아보지 못한다 (§3.3) |
| 파싱 없이 tree 만으로 0.0.1 주소를 낸다 | 주소가 위치 주소라 스냅샷마다 다를 수 있다. 안정 식별자를 따로 싣는다 |
| 고친 블록이 사라짐 + 생김이 아니라 바뀜으로 나온다 | 틈 안에서 자리로 짝을 짓는 것은 추측이다. 한 틈에서 둘을 지우고 다른 둘을 쓰면 바뀜 둘로 읽힌다 |
| 새 문서·지운 문서가 한 줄로 나온다 | 그 안의 블록은 보이지 않는다. `assemble` 로 본다 |
| 형식을 아는 곳이 `encode.ts` 하나로 남는다 | `encode.ts` 가 읽기 함수 셋만큼 커진다 |

틈 안의 자리 짝짓기(§3.2 단계 3)가 가장 약한 가정이다. 틀려도 잃는 것은 없다 — 바뀜 둘로 읽힌 것은
사실 사라짐 둘과 생김 둘이고, 어느 쪽이든 그 자리의 내용이 바뀌었다는 사실은 맞다. `--patch` 를 보면
어느 쪽인지 사람이 안다.

## 11. 남은 것

- 부모를 넘는 옮김 — 필요해지면 바뀐 하위 트리 안에서만 블록을 모아 짝을 지을 수 있다. 바뀌지 않은
  하위 트리는 여전히 건너뛰므로 R15.6 을 크게 해치지 않는다. 0.0.2 에서는 하지 않는다
- 문서 이름이 바뀐 것(옮긴 문서)을 알아보기 — 지금은 사라짐 + 생김이다. 문서 tree 주소가 같으면
  이름만 바뀐 것이므로 싸게 알아볼 수 있다. 다만 문서 meta 에 `id` 가 들어 있어 이름이 바뀌면 주소도
  바뀐다 — 알아보려면 meta 를 뺀 항목 목록을 비교해야 한다
