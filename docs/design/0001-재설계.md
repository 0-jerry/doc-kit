# rule-kit 재설계 — 판단기준 저작 시스템

상태: 구현 완료 · 날짜: 2026-09-15

> 구현하며 설계에서 달라진 곳은 본문에 그대로 반영했다. 무엇이 왜 달라졌는지는 §14 에 모았다.

## 1. 배경과 문제

현재 구현은 "규칙 문서"라는 단일 용도에 묶여 있다.

- 섹션 문법(`## Rule` → `## Why` → `## Examples` …)이 `schema.ts` 에 상수로 박혀 있다.
- `severity` / `enforced-by` / `applies-to` 같은 필드가 린터 연동을 전제로 고정되어 있다.
- 검증기 `validate.ts` 가 스키마 검사·섹션 규약·참조 무결성·문장 길이를 한꺼번에 안다. 책임이 뭉쳐 있다.
- 데이터 모델의 최소 단위가 "규칙 파일 1개"라서, 문서 안의 어느 진술이 어떤 맥락에 속하는지는 평문 문자열로만 남는다.

재설계의 목표는 **도구가 도메인을 모르게 하는 것**이다. 문서 종류와 문법은 사용자가 선언하고, 도구는 구조·책임 원칙·조작 프로토콜만 책임진다.

## 2. 확정된 요구사항

| 항목 | 결정 |
| --- | --- |
| 초기화 범위 | `src/` `test/` `rules/` 전부 삭제. TypeScript + unified/mdast + zod 스택 유지 |
| 프로토콜 | 세 층으로 분리 — 저작 문법 규약 / 코드 인터페이스 / 기계 조작 API |
| 트리 최소 단위 | 마크다운 블록 (문단·목록·코드블록·표·인용) |
| 트리 범위 | 문서별 독립 트리 + 상위 인덱스 |
| 보조데이터 | 대상(subject) · 주제(topic) · 역할(role) · 관계 링크 · 수명주기/적용범위 |
| 스키마 소유 | 사용자 정의 스키마 + 내장 프리셋 |
| 책임 제한 | 구조 위반은 오류로 차단, 정량 기준은 경고 (임계값 설정 가능) |
| 1차 소비자 | AI 에이전트 · 사람(문서 열람) |

비목표: 린터 연동, 자동 수정(autofix), 웹 에디터 UI. 1차 범위에서 제외한다.

## 3. 세 층과 의존 방향

```
  L1  저작 규약 (Authoring Protocol)
      .rulekit/schema.yaml — 문서 타입 · 섹션 구성 · 허용 역할 · 어휘
      사람과 에이전트가 "무엇을 어떻게 쓸 수 있는가"를 읽는 계약
                    │ 해석
                    ▼
  L2  문서 객체 모델 (Document Object Model)
      Document → Section → Block 트리 + Aux
      순수 데이터. 스스로 검증하지도 렌더하지도 않는다.
                    ▲ 조작
                    │
  L3  조작 프로토콜 (Operation Protocol)
      Command 객체 (JSON 직렬화 가능) — 에이전트와 CLI 의 공통 입력
```

의존 방향은 한 방향으로 고정한다.

```
  model  ←── schema
    ▲  ▲ ▲──── parse / serialize
    │  └────── validate
    └───────── api ──→ index ──→ render / query
```

- `model` 은 어떤 모듈도 import 하지 않는다. (원칙 P0)
- `validate` 는 `model` 과 `schema` 를 읽지만 어느 쪽도 수정하지 않는다.
- `render` `query` 는 `index` 의 산출물만 읽는다. 마크다운을 다시 파싱하지 않는다.

## 4. L1 — 저작 규약

### 4.1 파일 배치

```
<root>/
  .rulekit/schema.yaml        스키마 선언
  <collection>/<doc-id>.md    문서 1개 = 파일 1개
```

디렉터리명은 컬렉션 식별자, 파일명은 문서 식별자다. 스키마가 컬렉션별 문서 타입을 지정한다.

### 4.2 문서 문법

```markdown
---
type: principle           # 스키마가 정의한 문서 타입
id: 불변식은-생성자에서-검증한다
subject: [domain-layer]   # 대상 — 이 문서가 적용되는 곳
topic: [validation, invariant]
status: active
since: 2026-09-15
---

## 기준

<!-- rk: id=core role=norm -->
객체의 불변식은 생성자에서 검증하고, 검증에 실패하면 인스턴스를 만들지 않는다.

## 근거

유효하지 않은 상태의 객체가 존재할 수 없으면, 이후 모든 메서드가 상태 검사를 생략할 수 있다.

## 예시

<!-- rk: role=counter-example -->
```swift
init(age: Int) { self.age = age }   // 음수 나이를 통과시킨다
```

## 예외

<!-- rk: subject=[test-fixture] -->
테스트 픽스처 빌더는 의도적으로 무효 상태를 만들기 위해 검증을 우회할 수 있다.
```

세 가지 저작 채널이 있고, 각각의 역할이 다르다.

| 채널 | 담당 | 비고 |
| --- | --- | --- |
| frontmatter | 문서 전체의 보조데이터 | 하위 노드가 상속하는 기본값 |
| 섹션 제목 | 섹션 키 → 그 안 블록의 기본 역할 | 스키마가 `기준 → norm`, `근거 → rationale` 로 매핑 |
| `<!-- rk: … -->` 디렉티브 | 직후 블록 하나의 보조데이터 재정의 | 필요한 블록에만. 대부분은 생략 |

디렉티브를 HTML 주석으로 둔 이유: 마크다운으로서 유효하고, 일반 뷰어에서 보이지 않으며, 왕복(round-trip) 시 위치가 보존된다.

### 4.3 스키마 선언

```yaml
# .rulekit/schema.yaml
version: 1
extends: preset/principle        # 내장 프리셋 상속

documentTypes:
  principle:
    sections:
      - key: norm        heading: 기준    required: true   maxBlocks: 3
      - key: rationale   heading: 근거    required: true
      - key: example     heading: 예시    required: false
      - key: exception   heading: 예외    required: false
    order: strict                # strict | any
    frontmatter:
      subject: { kind: vocabulary, ref: subjects, required: true }
      topic:   { kind: vocabulary, ref: topics, many: true }
      status:  { kind: enum, values: [proposed, active, deprecated, superseded] }

roles:                            # 블록이 가질 수 있는 역할
  norm:            { childless: true, maxSentences: 3 }
  rationale:       {}
  example:         { requires: code }
  counter-example: { requires: code }
  exception:       {}

vocabularies:
  subjects: { source: .rulekit/subjects.yaml, closed: true }
  topics:   { closed: false }

relations:
  refines:     { target: norm, transitive: true, acyclic: true }
  conflicts:   { symmetric: true }
  supersedes:  { acyclic: true }
```

내장 프리셋은 `preset/principle` (원칙), `preset/convention` (컨벤션), `preset/decision` (결정 기록) 세 개로 시작한다. 프리셋은 그 자체가 같은 형식의 스키마 파일이므로 사용자 스키마와 특별히 다르지 않다 — 도구에 하드코딩된 문법은 없다.

## 5. L2 — 문서 객체 모델

### 5.1 트리

```
Document                 문서 1개. 루트이자 소유자
├─ Aux                   문서 수준 보조데이터
└─ Section               섹션. 스키마의 key 를 가진다
   ├─ Aux
   ├─ Section            중첩 가능 (깊이 상한은 스키마가 결정)
   └─ Block  ◀ 리프      문단 · 목록 · 코드 · 표 · 인용
      ├─ Aux
      └─ mdast 노드 (원문 보존용, 읽기 전용)
```

### 5.2 책임 분해

각 타입은 하나의 이유로만 변경된다.

| 타입 | 유일한 책임 | 하지 않는 것 |
| --- | --- | --- |
| `NodeId` | 주소 계산·비교 | 노드 내용을 모른다 |
| `Aux` | 보조데이터 보관·상속 병합 | 유효성 판단은 안 한다 |
| `Block` | 리프 내용 보관, 평문 추출 | 자식을 가질 수 없다 (타입 수준) |
| `Section` | 자식 순서 관리 | 내용 해석을 안 한다 |
| `Document` | 트리 소유, 노드 조회 | 다른 문서를 모른다 |
| `DocumentSchema` | 규약 질의 응답 (`sectionsOf(type)` 등) | 검사를 실행하지 않는다 |
| `Check` (개당 1클래스) | 원칙 하나 판정 | 다른 검사를 모른다 |
| `CheckRegistry` | 검사 수집·실행·진단 취합 | 판정 로직이 없다 |
| `Command` (개당 1클래스) | 트리 변형 하나 | 저장·출력을 안 한다 |
| `Indexer` | 문서 간 역인덱스·그래프 구축 | 파싱을 안 한다 |
| `Renderer` | 모델 → 출력 | 모델을 수정하지 않는다 |

인터페이스 스케치:

```ts
interface Node {
  readonly id: NodeId
  readonly kind: 'document' | 'section' | 'block'
  readonly aux: Aux
}

interface Branch extends Node { readonly children: readonly Node[] }
interface Leaf   extends Node { readonly children?: never }   // 타입 수준 차단

interface Block extends Leaf {
  readonly kind: 'block'
  readonly form: 'paragraph' | 'list' | 'code' | 'table' | 'quote'
  text(): string
}
```

### 5.3 보조데이터(Aux)

```ts
interface Aux {
  role?: RoleId                    // 역할 — 단수. 혼재가 타입 수준에서 불가능
  subject: readonly SubjectId[]    // 대상 — 어디에 적용되는가
  topic: readonly TopicId[]        // 주제 — 무엇에 관한 것인가
  lifecycle: Lifecycle             // status · since · until · 강제 수준
  relations: readonly Relation[]   // 다른 노드로의 링크
}
```

**상속과 재정의.** 보조데이터는 조상에서 자손으로 흐른다. 자손이 같은 키를 선언하면 그 가지에서만 덮어쓴다. 잎마다 전체 맥락을 다시 쓰지 않아도 되므로 문서가 짧아지고, 에이전트는 어느 노드에서든 `effectiveAux()` 한 번으로 완전한 맥락을 얻는다.

| 키 | 병합 규칙 |
| --- | --- |
| `role` | 상속하지 않는다. 섹션 기본값 또는 명시 선언 |
| `subject` | 상속. 자손이 선언하면 **교집합**으로 좁아진다 (확장 불가 — P7) |
| `topic` | 상속. 자손 선언은 합집합 |
| `lifecycle` | 상속. 자손이 상위보다 넓은 상태로 승격 불가 |
| `relations` | 상속하지 않는다. 선언한 노드에만 붙는다 |

`subject` 가 좁아지기만 하는 것이 핵심이다. 하위 블록이 상위 문서보다 넓은 대상을 주장할 수 없으므로, 문서가 슬금슬금 책임을 늘리는 일이 구조적으로 막힌다.

### 5.4 주소 체계

```
principle/불변식은-생성자에서-검증한다#norm/2      위치 주소 (편집용)
principle/불변식은-생성자에서-검증한다#core        안정 주소 (참조용)
```

위치 주소는 편집이 일어나면 바뀐다. 따라서 **관계 링크의 대상이 되는 노드는 디렉티브에 명시적 `id=` 를 가져야 한다** (없으면 오류). 링크되지 않는 대다수 블록은 식별자를 붙일 필요가 없다.

## 6. L3 — 조작 프로토콜

명령은 JSON 객체다. 에이전트가 그대로 내보내고, CLI 가 같은 형태를 만들고, 테스트가 같은 형태를 검증한다.

```json
{ "op": "block.insert",
  "at": "principle/불변식은-생성자에서-검증한다#exception",
  "position": "end",
  "form": "paragraph",
  "aux": { "subject": ["test-fixture"] },
  "text": "테스트 픽스처 빌더는 …" }
```

| 명령 | 사전조건 |
| --- | --- |
| `document.create` | 스키마에 존재하는 타입, 식별자 미사용 |
| `document.setAux` | 어휘가 닫힌 경우 값이 어휘에 존재 |
| `section.ensure` | 스키마가 허용한 섹션 키, 순서 규약 충족 |
| `block.insert` / `update` / `remove` | 대상 섹션이 `maxBlocks` 를 넘지 않음 |
| `node.move` | 같은 문서 내. 대상의 `subject` 가 새 부모보다 넓지 않음 |
| `relation.link` / `unlink` | 양끝이 안정 식별자를 가짐, 비순환 제약 충족 |

모든 명령은 `(Document, Command) → Result<Document, Diagnostic[]>` 이다. 원본을 변형하지 않고, 파일도 쓰지 않는다. 쓰기는 `serialize` 가 별도로 한다. 이 분리 덕에 에이전트는 명령 배열을 던져 놓고 **먼저 진단만 받아본 뒤** 커밋할 수 있다 (`--dry-run`).

## 7. 책임 과다 방지 원칙

| # | 원칙 | 강제 방식 | 코드 |
| --- | --- | --- | --- |
| P0 | 모델은 아무것도 import 하지 않는다 | 의존성 검사 (CI) | `DEP001` |
| P1 | 리프는 자식을 갖지 못한다 | 타입 시스템 | — |
| P2 | 한 블록은 역할을 하나만 갖는다 | 타입 시스템 (`role` 단수) | — |
| P3 | 규범 진술 블록은 한 가지만 말한다 | 경고 — 문장 수 임계 초과 | `STR001` |
| P4 | 섹션은 스키마가 정한 블록 수를 넘지 않는다 | 오류 | `STR002` |
| P5 | 섹션 구성·순서는 스키마를 벗어날 수 없다 | 오류 | `SCH001-003` |
| P6 | 트리 깊이는 스키마 상한을 넘지 않는다 | 오류 | `STR003` |
| P7 | 자손의 `subject` 는 조상보다 넓을 수 없다 | 오류 | `AUX001` |
| P8 | 닫힌 어휘 밖의 대상·주제는 쓸 수 없다 | 오류 | `AUX002` |
| P9 | 형제 노드 수는 임계값을 넘지 않는다 | 경고 | `STR004` |
| P10 | 내용 복제 대신 관계 링크를 쓴다 | 경고 — 동일 다이제스트 발견 | `REF001` |
| P11 | 참조 대상은 존재하고 비순환이어야 한다 | 오류 | `REF002-003` |

타입 시스템으로 막을 수 있는 것은 검사기를 만들지 않는다(P1, P2). 표현 불가능한 위반은 검사할 필요가 없다.

검사기는 하나당 클래스 하나다.

```ts
interface Check {
  readonly code: string
  readonly severity: 'error' | 'warning'
  run(node: Node, ctx: CheckContext): Diagnostic[]
}
```

`CheckContext` 는 스키마와 조상 체인만 제공한다. 검사기는 파일 시스템도, 다른 문서도, 다른 검사기도 볼 수 없다.

## 8. 인덱스와 에이전트 질의

문서 트리는 서로를 모른다. 문서 간의 것은 전부 인덱스가 담당한다.

```
.rulekit/out/
  documents/<collection>/<name>.json   문서별 노드 기록 (Aux 해석 완료본)
  index.json    bySubject · byTopic · byRole · byStatus · byCollection 역인덱스
  graph.json    관계 그래프
```

에이전트 진입점은 두 개다.

```bash
rulekit query rules --role norm --subject domain-layer --status active
rulekit context src/domain/Order.swift --root rules
```

`query` 는 조건에 맞는 **규범 진술만** 돌려준다. 각 항목에는 조상 breadcrumb, 해석된 보조데이터, 근거 노드 링크가 붙는다 — 근거 본문은 붙이지 않는다. 에이전트가 "지켜야 할 것"만 싼값에 읽고, 왜인지 궁금할 때만 한 번 더 호출하게 만드는 구조다.

`context` 는 파일 경로를 대상 어휘로 역매핑해 그 파일에 적용되는 판단기준을 모은다. 대상 어휘와 경로의 매핑은 `subjects.yaml` 이 소유한다 — 도구는 경로 규칙을 모른다.

## 9. 사람용 출력

`rulekit render` 는 `documents/*.json` 과 `index.json` 만 읽어 정적 HTML 을 만든다. 마크다운을 다시 파싱하지 않는다. 대상·주제별 색인과 관계 그래프를 함께 낸다.

## 10. 디렉터리 구조

```

## 11. 트레이드오프

| 결정 | 얻는 것 | 잃는 것 |
| --- | --- | --- |
| 블록 단위 트리 | 진술 단위 조회·링크·상속. 에이전트 토큰 절감 | 노드 수가 10배 늘고 왕복 보존이 까다로워진다 |
| HTML 주석 디렉티브 | 마크다운 호환, 일반 뷰어에서 무해 | 문법이 눈에 덜 띄어 작성자가 잊기 쉽다 |
| 사용자 정의 스키마 | 도메인 독립성 확보 | 첫 사용 비용 증가 — 프리셋으로 상쇄 |
| 문서별 트리 + 인덱스 | 경계가 깔끔, 문서 단위 병렬 처리 | 문서 간 질의는 인덱스 재빌드에 의존 |
| 불변 모델 + 명령 객체 | dry-run, 되돌리기, 테스트 용이 | 대용량 편집 시 복사 비용 |
| 타입 시스템 우선 강제 | 검사기 수가 줄고 위반이 애초에 불가능 | 스키마로 표현 못 하는 규약은 런타임으로 밀림 |

## 13. 다시 볼 지점

- ~~**왕복 보존**이 실제로 견디는가~~ — 견딘다. 각 노드가 자기 원문 조각과 그 조각이
  원문에서 차지한 범위를 들고 다니고, 조각들이 문서 전체를 겹침 없이 덮는다.
  빈 파일 · CRLF · 끝 줄바꿈 없음 · 떠도는 블록 · 중첩 섹션 · 표/목록/인용 ·
  연속 디렉티브 · 빈 줄 없이 맞닿은 블록까지 바이트 단위로 같다.
- ~~**간격**~~ — 원래 이웃이었는지를 원문 범위로 가려서 해결했다. 원래 이웃이던
  조각끼리만 작성자가 쓴 간격을 그대로 두고, 그 밖의 경계에는 빈 줄을 보장한다.
  남은 제약은 이 범위가 **한 문서 안에서만** 뜻이 있다는 것이다 — 노드를 다른 문서로
  옮기는 명령이 생기면 그때 범위를 버려야 한다.
- **대상 어휘의 크기**. 어휘가 수백 개로 늘면 닫힌 어휘가 부담이 된다. 계층형 어휘(`domain-layer/order`)로 확장할 여지를 남겨둔다.
- **인덱스 증분 갱신**. 문서 수가 수백을 넘기 전까지는 전체 재빌드로 버틴다.
- **디렉티브 의존도**. 실제 작성에서 디렉티브가 자주 필요해지면, 섹션 기본 역할 매핑이 부족하다는 신호다. 스키마 쪽을 보강할 것.

## 14. 설계에서 달라진 것

| 설계 | 구현 | 왜 |
| --- | --- | --- |
| `index/` | `workspace/` | `src/index.ts` 와 헷갈린다 |
| 진단 타입이 `validate/` 안 | `diagnostic/` 을 따로 | 파싱·조작도 같은 형태로 보고해야 하는데, 그러려면 검증기에 의존하게 된다 |
| 프리셋을 YAML 파일로 | 프리셋을 TS 모듈로 | tsc 가 YAML 을 dist 로 옮기지 않는다. 형식과 로더는 사용자 선언과 똑같다 |
| `#core` 와 `#norm` 을 문법으로 구분 | 안정 식별자 → 위치 걸음 순으로 해석 | 걸음이 하나인 주소는 문법만으로 가릴 수 없다. 충돌은 `AUX004` 가 잡는다 |
| 블록의 역할을 질의 시점에 해소 | 파싱 시점에 해소 | 이후 층이 전부 규약을 들고 다녀야 한다. 쓸 때는 규약과 비교해 기본값이면 다시 적지 않는다 |
| 대상 어휘는 값 목록 | 값 → 경로 글롭 매핑 | `rulekit context <파일>` 이 성립하려면 경로 규칙을 누군가 소유해야 하는데, 그것이 도구여서는 안 된다 |
| 원칙 번호 P0~P11 | 진단 코드로 정착 | 표의 코드가 실제 구현이다. P10(내용 복제)은 문서 간 검사이므로 `REF001` 로 옮겼다 |
